How to read this. When a user is scoped to more than one passkey profile, Entra allows a passkey if it satisfies at least one of them. Profiles do not stack toward strict, they union toward permissive. Exclusion from the passkey policy is the one thing that beats inclusion. Each user's effective policy below is that union. Conditional Access works the other way: every applicable policy must be satisfied, so the admin attack paths show both what an admin can register and what they can sign in with. SMS and voice retire on 1 Feb 2027 with a blocking passkey prompt and no opt-out; Global Admins and external users follow on 1 Jul 2027.

Admin attack paths

For each privileged user: what they can register, what they hold, what Conditional Access lets them sign in with, and who could bootstrap a new credential. Registration resolves by union; Conditional Access by intersection.

Rule definitions

R1 Overlap weakening
A privileged user can register a weaker passkey than the admin profile intends, because at least one scoped profile allows it.
R2 Weak key already held
A privileged user already holds a synced or unattested passkey.
R3 Deadline cohort
User's only MFA is SMS or voice. They hit a blocking passkey registration prompt on 1 Feb 2027 (Global Admins and external users: 1 Jul 2027).
R4 Auto-enabled admin
A privileged SMS/voice user sits in an 'all passkey types' profile, the shape Microsoft auto-enabled on 1 Sep 2026.
R5 AAGUID trap
A user holds a passkey that none of their scoped profiles accepts. Microsoft blocks keys whose AAGUID is not permitted, so they lose sign-in with it.
R6 Attestation illusion
A profile is relied on as 'attested' but synced passkeys cannot be attested, or its users can bypass it through another profile.
R7 No phishing-resistant method
A privileged user has no phishing-resistant method registered.
R8 Campaign gap
The registration campaign will not reliably move the SMS/voice cohort to passkeys before the deadline.
R9 Excluded but privileged
A privileged user is excluded from the passkey policy. Exclusion beats every inclusion, so they cannot use passkeys at all.
R10 Policy hygiene
Profile count, list size, unused or dangling references, and auto-added Authenticator AAGUIDs.
R11 Synced passkey at sign-in
Every Conditional Access policy covering an admin accepts a synced passkey. Microsoft's built-in phishing-resistant strength does; only a FIDO2 AAGUID allow list stops it.
R12 Weak admin sign-in gate
An admin is covered by no enforced MFA policy, or every policy covering them accepts SMS or voice.
R13 TAP bootstrap path
Temporary Access Pass is enabled for an admin, so anyone who can issue them a TAP can register a passkey on their account.
R14 Tamperable policy group
A group that decides passkey, TAP or Conditional Access scope is not role-assignable, so non-privileged admins or owners can change who is in it.
R15 Migration incomplete
Legacy MFA and SSPR settings still govern SMS and voice because the authentication methods migration is not complete.
R16 Sign-in evidence
Sign-in logs show admins using SMS, voice or synced passkeys.

Per-user FIDO2 detail is exported for privileged users and the SMS/voice cohort only, which keeps Graph calls bounded. Rules that read registered keys (R2, R5) cover that scope.
