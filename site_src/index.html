Your admins can register a weaker passkey than your policy says.

EffectivePasskey computes the passkey policy each Entra ID user actually gets after overlapping passkey profiles resolve, and predicts who will be blocked when Microsoft retires SMS and voice. It runs offline on read-only exports and never holds a token. It is free and open source under the MIT licence, with no paid tier, no sign-up and no telemetry.

The flaw, in one picture

Microsoft Learn: when a user is scoped to more than one passkey profile, a passkey is allowed if it satisfies at least one of them. Not most-restrictive-wins.

Admin profile strict

  • Device-bound passkeys only
  • Attestation required
  • Security key allow list
+

All Users profile loose

  • All passkey types
  • Synced passkeys allowed
  • No attestation
Effective result for a Global Admin in both: they can register a synced, unattested passkey. The portal shows both profiles side by side and never computes this per user. EffectivePasskey does.

Registration is a union. Sign-in is an intersection.

Passkey profiles let a passkey in if any profile allows it. Conditional Access lets a credential through only if every applicable policy accepts it. EffectivePasskey evaluates both and draws an attack path per admin: what they can register, what they hold, what they can sign in with, who could bootstrap a new credential with a Temporary Access Pass, and what the sign-in logs show.

Run it on your tenant

# 1. Export (PowerShell 7, read-only delegated scopes; you run it, the analyzer never sees a token)
./collector/Export-EffectivePasskeyData.ps1 -OutputPath ./my-export

# 2. Analyze (Python 3.10+, no dependencies)
python3 -m effective_passkey analyze ./my-export -o ./report

# 3. Propose fixes, simulated before you touch anything
python3 -m effective_passkey remediate ./my-export -o ./plan
